# Scope

完整目标规格为 specs/smart-routing/spec.md。所有实现都在本 change 内按依赖推进，不把速度、成功率、综合或自定义另作未来需求。

- Key 路由模式、五策略入口、动态排除项、自定义两步配置、手动顺序、健康/价格和安全说明。
- 当前用户获权业务分组候选、所有真实协议入口、请求级 attempt 去重/预算、实时健康避让、组内既有 priority/weight。

- 新智能异步提交耐久凭据和窄范围对账，不向旧Key通用Task扩展新的耐久提交合同；共享余额接点统一同步DB权威，启用前停写排空旧batch，禁止新旧余额模式混用；不改变旧固定/Auto调度计价语义。

# Decisions

1. 候选单位是（客户端模型、获权业务组），不是物理Channel。组内保priority/weight，硬过滤后抽取未尝试渠道；新模式全局预算不被组切换重置。
2. 旧Key没有扩展策略行即legacy；固定/Auto/空group继承和显式空auto列表原样保留。旧Auto只在编辑该旧Key时显示“旧版Auto（保持原行为）”兼容项；新建不提供此第三种新模式。用户明确切换才写新策略。
3. 算法 smart-routing-v1：综合价格20%、成功率40%、速度25%、实时空闲15%；24h排名与1h卡片，60s/5min健康避让。全部数值在完整Spec公开，作为工程提案由组长审定，不让用户选择权重。
4. 自认证接口用 /api/mowan/smart-routing/self，Bearer只能约束当前Key；控制台管理仍走既有 /api/token/ 的UserAuth/PAT/Casbin。写开关仅控制台可改，self DTO不包含。
5. 配置扩展以token_id唯一行、JSON文本与乐观version保存；无扩展行保旧语义，读失败与无行严格区分。删除Key联动清理，不改上游Token核心schema。
6. 数据聚合用现有DB/Redis或内存，健康为建议性信号，任何观测故障不能扩大权限或绕资金检查。详细租约、聚合幂等和故障降级见Spec。
7. 单change，内部按配置/观测→选路→计费与协议→UI→检查串行。自认证GET也采用完整有效Key门禁；审计复用既有尽力写并显式暴露故障，不承诺与LOG_DB原子提交。旧客户端明确传legacy路由字段的新建保原意图，全未传才用新默认。组长审核工程提案后向用户展示完整Shape，不把工程参数重新抛给用户。
