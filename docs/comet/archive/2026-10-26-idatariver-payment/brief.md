# 目标

在 new-api 的现有钱包和支付设置中接入 iDataRiver，使用户购买商户现有充值商品后获得对应钱包额度；支付结果经服务端主动查单核实后，以数据库事务保证只入账一次。

需求来源：用户提供的 https://docs.idatariver.com/zh/guide/merchant_api.html 及商户信息。商户 ID 为 `6adaf86e4a9d53fa7ffbfa10`，分类代码为 `2001`；开发者密钥仅用于服务端配置，不在正式文档、代码、浏览器响应或日志中保存原值。项目实际所有者与提供的商户 ID 相符。

# 范围

- 首版接入钱包充值。复用已上架项目 `6adb0ecdc5c1b963f6862493` 的五档商品；10/20/30/50/100 USD 分别增加等值美元钱包额度，内部按现有 `QuotaPerUnit` 换算。平台手续费不增加钱包额度。不同显示货币沿用现有余额展示规则。
- 设置页增加 iDataRiver 配置入口：启用状态、商户 ID、服务端开发者密钥、项目 ID、SKU 与充值额度映射；回调域名沿用现有可信站点/回调地址设置并强制校验 HTTPS 域名。配置通过现有受保护的选项接口管理，密钥不回显，留空保留原密钥。
- 钱包展示已配置的固定充值包。服务端核实商品归属、上架状态和价格，再创建订单；每单数量固定为 1，不使用优惠券或推广码。仅显示该订单返回且启用的支付方式，支付链接由服务端向平台取得。
- 创建支付前保存订单与入账快照，记录当前商户、项目、SKU、价格、充值额度及订单关联。配置或商品价格后续变动不改变既有订单的入账额度；平台实际订单与快照不一致时拒绝继续支付或入账。
- 支付回跳落在本站钱包订单页；回跳本身不视为付款。回调及用户主动“检查支付状态”均通过服务端查询平台订单后进入同一结算流程。
- 回调识别已支付、过期和退款。平台查单确认REFUND后，若该订单已入账且钱包余额足够，通过事务幂等扣回该订单实际入账额度；余额不足时不部分扣款、不产生负余额，记录异常交管理员处理。未入账的退款订单不扣余额，并禁止迟到支付通知再次充值。该流程不包含调用平台发起退款。
- 当前 Native change 仅实现独立的 iDataRiver 支付能力；自动建议关联的管理员概览统计不是本次需求，不修改其产品行为。

### 修改

- `controller/topup.go`、`controller/option.go`、`controller/payment_webhook_availability.go` — 返回安全的充值配置、配置校验及支付启用判断。

# 非目标

- 订阅购买、自动续费、任意金额、多件数量、优惠券和充值折扣。
- 调用平台自动发起退款、部分退款及跨渠道资金对账；公开文档未提供发起退款接口。本站自动回收已退款订单的额度纳入本次范围，余额不足转人工处理。
- 平台项目、商品、库存、价格、License、代理商或机器人管理。
- 修改站点已有支付渠道的结算规则、身份认证体系或管理员统计定义。
- 在没有额外上线指令时部署远程站点、修改DNS/证书、替换运行中的支付配置、进行真实付款或退款。
- 把“无需实名”作为软件承诺；该描述不构成API能力或审核政策保证。

# 约束与不变量

- 金额和额度使用现有精确换算与边界检查，不用截断或静默夹值容忍异常；拒绝零、负数、溢出、未配置SKU、跨商户订单及价格不符。
- 结算快照在创建时保存，数据库保证本地订单、平台订单与用户的稳定唯一关联。数据写入失败时不得返回可继续支付的链接。
- 幂等依赖数据库事务及订单状态条件，不仅依赖进程内互斥锁。复用 `lockForUpdate`、`creditTopUpQuota`、额度上限、缓存与充值日志规范。
- 在同一事务中完成成功状态与钱包余额更新；任何一步失败应回滚，并允许后续查询重试。重复、并发、重放、退款后迟到通知均不重复入账。
- 已有合规确认规则继续生效；禁用新的下单入口后，持有有效配置的既有订单仍可完成查单、结算及回调，避免已付款无法到账。
- 对外响应仅包含必要的商品、订单和支付信息。密钥、平台库存、数字内容、随机查询凭据及完整平台响应不得泄露到浏览器或日志。
- API固定平台HOST、验证TLS、禁用泄露鉴权的跨域重定向；回调与回跳URL由可信服务端配置生成，客户端不能指定任意地址。

# 验收示例

- 管理员配置平台信息并保存后可重新打开设置；密钥不回显，留空保留；非管理员不能读写配置，普通客户端和日志看不到开发者密钥或数字库存。配置不完整、未启用或未满足已有支付确认规则时不开放新的下单。
- 钱包正确展示配置的10、20、30、50、100美元充值包；每单1件，充值额度与选定档位一致；服务端拒绝未配置SKU、错误归属、下架、零价、价格变化或不支持定价的商品，不受客户端金额篡改影响。
- 登录用户选择充值包后创建唯一关联的本地/平台订单，展示该订单可用支付方式及平台应付币种/金额，获取有效支付链接并返回本站钱包；不支持的方法被拒绝，回跳不直接入账，支付链接生成失败可明确提示并重试。
- 平台HTTP错误、code非0、无效JSON、响应缺字段、零价无链接和超时均返回可理解的失败结果，不给钱包加额度；不会把平台业务错误当作成功，不输出敏感原始响应。
- 伪造、重放、未知订单、跨商户/项目/SKU、金额或数量不符的回调不能入账；真实已支付订单经服务端查单核对后入账。回调使用HTTPS域名，成功在5秒内返回200/201，暂时失败返回可重试状态。
- 同一已支付订单的重复或并发回调以及主动查询最多产生一次钱包增加和一次成功充值日志；钱包上限或事务失败时状态和余额一并回滚，之后可重试；改配置不改变旧订单快照。
- NEW、EXPIRED、REFUND和未知状态不新增余额。真实REFUND经服务端核实后，已入账且余额足够的订单自动扣回原入账额度一次并写回收记录；余额不足时不部分扣款、不产生负余额，标记待人工处理。未入账退款不扣款。重复/并发退款、退款与消费或结算竞争、数据库失败不会重复扣款或突破余额检查，失败事务可重试；退款后迟到支付不重新发额度。
- 本人可以检查待支付订单状态并在回调遗漏后经同一核实流程补账；其他用户和未登录客户端不能查询或触发他人订单核查；已有订单在停止新下单后仍能正常核实与结算。
- 新界面复用已有业务与基础组件，具备加载、空、失败、禁用状态及键盘/可访问名称；支付宝和微信展示平台要求的网络提示；新增文案七种语言齐全，语言切换及金额显示沿用项目格式化约定。
- SQLite、MySQL、PostgreSQL真实实例均验证新订单、并发幂等、金额拒绝、钱包上限与事务回滚；涉及模型迁移时验证新建库和最新发布版代表库升级且重复启动两次。相关测试、前端类型检查、涉及文件lint及构建通过，旧支付充值与历史记录显示保持兼容。

# 验证要求

先写能保护实际支付结果与安全边界的定向回归用例，复用现有测试入口；不为每层重复增加同一套测试。开发期执行定向检查，正式检查由 Runtime 在候选实现冻结后执行，再由新的只读 Verifier 独立验收所有条目。

真实资金支付不属于默认验证授权；平台只读查询和必要的未支付测试订单可用于联调。正式支付成功证据若无法取得须如实标明，不能用模拟回调声称已完成真实支付。生产回调需要可访问的HTTPS域名，可在独立上线步骤配置并实测。

# 生产地址

用户已提供前端与API统一使用 `https://mw.vistalineglobal.com`。平台回调地址规划为 `https://mw.vistalineglobal.com/api/user/idatariver/notify`；支付回跳使用该域名下的现有钱包页面，带本地订单标识供本人核查。固定可信Origin，不接受客户端覆盖。正式上线前核实反向代理开放回调且无需登录、不会重定向到登录页，并测试平台可达性；公网GET可访问不等于平台POST回调联调通过。

# 退款决定

用户已明确选择“自动扣回，余额不足转人工”。平台查单确认REFUND后，已入账订单在余额足够时通过事务仅扣回实际发放额度一次；余额不足则不部分扣款、不产生负余额，记录异常交管理员处理。未入账的退款订单不扣款且禁止以后入账。扣款、回收状态和防重复凭据必须原子提交，使用数据库条件更新应对与消费并发；与付款结算竞争时以同一订单的数据库状态协调。回收记录需要可核查，不能把成功充值日志重复记成新的充值。2026-10-26重新完整核实公开商户API：支持退款状态查询和退款回调，未提供发起退款接口；该自动化仅指本站退款结果处理。此决定替代原先“所有退款均人工处理”的草案。

# 决定

采用一个 Native change，后端结算与钱包界面紧密耦合，单独拆分会增加共享支付流程的协调成本。实现期间沿用当前工作区，保留已有无关修改。以上方案尚待完整Shape确认；确认后进入Build。
